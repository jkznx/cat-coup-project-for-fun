# Public rendering and loading audit — 2026-10-28

Target: https://cat-coup.jukrachai-crybaby.space/. The running server was not restarted. No microphone, game commands, load generator, external API spend or existing-room changes were used. Source UI/game behavior was not changed by this audit.

## Method and limits

12 page loads: three cold/primed-reload pairs at each of 1440×1000 and 390×844. Fresh Edge browser contexts isolate browser cache for each pair; CDN and OS DNS caches were not cleared. Network emulation: 500,000 download bytes/s, 125,000 upload bytes/s, 40ms additional latency, 4× CPU slowdown. Actual Internet/Tunnel latency is additional and variable. Reduced motion removes entrance timing from comparison. Test browser version and timestamps are in the JSON.

The custom **artwork ready** time waits for the page load, welcome surface, document fonts, original cat sprite response completion and two animation frames. It is not a Web Vital and not a full game-connect/readiness measurement. LCP was the homepage H1 in every sample, so a good LCP does not imply the cat artwork has finished loading.

This is a small laboratory sample from one Windows PC, not real-user p75, not Lighthouse scoring and not worldwide performance. No INP result is claimed. The recorded help-button event durations are sparse lab observations only. Real-user INP/LCP distributions and six-player runtime profiling remain unmeasured in this run.

The historical JSON field `documentTtfbMs` is HTTP responseStart minus requestStart; it excludes DNS/connection establishment and is not whole-navigation TTFB. Future script runs additionally record navigationTtfbMs explicitly. A separate lightweight health comparison below measures fetch-to-headers including connection setup.

## Evidence-backed findings

1. **P1 — initial artwork dominates delivery.** `/assets/cat-court-lossless.webp` is 2,195,468 bytes, approximately 92% of measured cold page transfers. The sprite finishes much later than the text LCP. Keep the original artwork source, then consider a smaller responsive or high-quality lossy delivery derivative; compare visual quality before publishing. The three new Vintage portraits are not loaded on the homepage and are not the dominant homepage cost.
2. **P1 — public network path is variable.** Three local `/health` reads took 2, 3 and 32ms to headers (first included connection overhead). Public reads took 768, 2,189 and 2,573ms. This implicates the Internet/edge/Tunnel path, rather than proving slow game logic. It does not isolate ISP versus Cloudflare edge versus tunnel transport.
3. **Compression and cache are already working.** Actual public JS and CSS responses use zstd. First cold JS was about 121,714 encoded bytes from 359,283 decoded bytes; CSS about 22,377 from 50,888. Static assets advertised max-age=14400; observed edge statuses included REVALIDATED/EXPIRED and effective browser reuse. HTML remained DYNAMIC with max-age=0. Warm browser reload transfer fell to approximately 3KB. Do not add redundant compression work or cache private game state.
4. **P2 — mobile visual priority can improve.** The homepage card fan has small, partly overlapped role labels, and the room form sits below the first mobile viewport. These are usability/hierarchy concerns, not horizontal overflow. Keep the illustrated style while making the primary join/create path easier to reach.
5. **P2 — startup main-thread work warrants attribution before changing code.** Under 4× CPU slowdown, cold runs recorded long tasks up to 590ms. Public responses include Cloudflare-injected challenge/analytics scripts in addition to the app. This audit does not attribute the long tasks to React, GSAP or injected scripts; capture a trace before optimizing those components.

No page JavaScript errors, failed non-Socket.IO requests or horizontal overflow were recorded in the 12 measured homepage loads. Observed help-button events, where captured, were 40–144ms; these are not a field INP result.

## Rendering confirmation

Classic and Vintage lobbies were checked at 320, 390, 768, 1024 and 1440px: ten combinations, zero horizontal overflow and zero page JavaScript errors. A single temporary lobby was created and explicitly left on each of two inspection runs; no game was started. The first captures showed blank Vintage portrait slots because capture preceded CSS background-image completion; they were discarded and replaced by captures after an image response/decode check. Confirmation returned HTTP 200 with image/webp; the switch-to-image-response interval was 1,583ms in that unthrottled run. The portraits decode and render correctly. This is delayed loading, not evidence of a missing asset. Raw confirmation is docs/performance/2026-10-28-render.json.

Vintage remains visually distinct, the original five painted cats still load, and the new three-role artwork matches the correct source. At 320px the bot utility band wraps its Add test bot label to three lines and the room actions sit far below the mode details. This is an additional P2 compact-lobby improvement, not a viewport overflow failure. The current audit does not create an active game or certify six-player in-game frame rates.
